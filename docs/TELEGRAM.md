# Telegram Qaldyq и работа с доменом

Бот дополняет существующий проект NOVA_QALQYQ. Студенческий Mini App — та же страница `/student/`, а не отдельное приложение с копией заказов. Измерения используют `ReportDomain.save_quick`, общую проверку из веба, `org_categories`, единицы kg/l и блокировку периодов. Заказы, остатки, отмена и выдача остаются в `mod_student.py`; права проверяющего и администратора не меняются.

## Быстрый запуск Windows

Из корня **этого** репозитория:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install "aiogram>=3.31,<4"
Copy-Item .env.example .env
```

Если `.env` уже заполнен, не заменяйте его образцом. Впишите локально `TELEGRAM_BOT_TOKEN`, при необходимости `TELEGRAM_BOT_USERNAME`. Токен не коммитится. Бот и веб должны использовать один `QALDYQ_DB=data/qaldyq-v5.4.sqlite3`. Старую базу `data/qaldyq.sqlite3` от прежней версии сюда не переносите.

Если общая база ещё не создана, один раз выполните `python server.py`, дождитесь запуска и остановите сервер. Миграции добавочные и повторяемые; перед обновлением существующей базы сохраните резервную копию.

Для локальной разработки установите cloudflared из официального источника и запустите:

```powershell
.\start-telegram.ps1
```

Сценарий читает `.env`, проверяет бота через `getMe` без отправки сообщений, запускает сервер, polling-воркер и при необходимости HTTPS-туннель. Туннель создаётся только при пустом локальном адресе либо адресе `trycloudflare.com`. Постоянный HTTPS-домен сценарий **не заменяет**. Статус и журналы — `data/telegram-runtime/`; секреты не выводятся. Повторный запуск при работающем экземпляре не создаёт новый. `-CheckOnly` проверяет локальные зависимости без подключения к Telegram.

## Сотрудник и студент

- `/start` показывает команды. `/link` выдаёт одноразовую ссылку на `/telegram-link.html`: войдите в существующий веб-аккаунт, проверьте email, текущую роль и Telegram ID и явно подтвердите. Код случайный, 256 бит, хранится только хеш, живёт 10 минут; новый код аннулирует старый. POST требует веб-сессии и CSRF. Имя и username Telegram не используются для поиска аккаунта.
- Совместим и код из существующего студенческого профиля: `/link КОД`. Код стал длиннее (128 бит), одноразовость сохранена. Другую привязку без явного отключения бот не перезаписывает.
- `/employee`: необходим активный `operator` или `admin` с организацией. Выбор доступного вида → количество в его единице (kg или l) → этап образования → действующий способ утилизации → фото до 2 МБ либо `/skip` → подтверждение. Измерение добавляется в черновой отчёт через общий веб-сервис. Фото начинает отдельный черновик, чтобы не заменить ранее прикреплённое доказательство. Итоги показывают кг и литры раздельно. `/cancel` отменяет ввод; сессия живёт 30 минут.
- Поданный или принятый период заблокирован тем же `mod_period.ensure_unlocked`. Отправка, возврат с обязательным комментарием и приёмка выполняются в вебе по существующим правам, включая `can_review`. Бот не получает права принимать отчёты.
- `/student` для привязанного пользователя открывает студенческий сценарий. Для нового пользователя без аккаунта эта команда явно создаёт только обычный низкопривилегированный профиль студента; существующий аккаунт нужно связывать через `/link`. Доступны язык ru/kk, действующие публичные столовые, их опубликованное меню, свои заказы и кнопка Mini App.
- `/subscriptions` управляет видами существующих уведомлений: `order_status`, `pickup_reminder`, `report_deadline`, `report_returned` и другими поддерживаемыми проектом. Для новой привязки они выключены. `/stop` выключает все. Изменение подписок в веб-профиле влияет на ту же таблицу `subscriptions`. `/unlink` отключает привязку и ожидающие уведомления, не меняя владельцев старых заказов.

Всё работает только в личном чате. Роль, активность и организация заново читаются из `users`, включая момент подтверждения. Telegram сам по себе служебную роль не подтверждает.

## QR-код

Во вкладке **«Асхана QR-кодтары»** добавлена отдельная карточка Telegram со ссылкой и скачиванием SVG. Данные QR — `https://t.me/<username>`. Поэтому изменение домена веб-приложения не требует перепечатки QR бота. Существующие QR столовых продолжают работать как раньше.

По умолчанию указан публичный username текущего бота `Qalqyq_NOVA_bot`. Его можно изменить в `TELEGRAM_BOT_USERNAME`; при запуске воркер обновляет имя в общих настройках по проверенному ответу `getMe`. Токен в QR и API bootstrap не попадает.

## Mini App

При старте воркер ставит кнопку меню бота на `<QALDYQ_PUBLIC_URL>/student/`; inline-кнопка ведёт туда же. Дополнительно можно настроить Main Mini App в BotFather на этот URL. После смены домена перезапустите воркер, чтобы обновить кнопку.

Telegram SDK подключён только к существующей студенческой странице. Сырой `Telegram.WebApp.initData` передаётся своему серверу в `Authorization: tma …`, не в URL и не в localStorage. Сервер на **каждом** защищённом запросе проверяет HMAC-SHA-256 по официальному алгоритму Telegram, обязательные поля, уникальность ключей и `auth_date` (300 секунд, до 30 секунд расхождения часов вперёд). Старую сессию нужно открыть заново. `initDataUnsafe` не служит доказательством личности.

После проверки используется активный привязанный аккаунт из общей базы. Mini App авторизация ограничена `/api/me` и `/api/student/*`; служебные API закрыты. Обычный веб сохраняет cookie + CSRF, при HTTPS cookie получает Secure. Разрешение Telegram SDK и встраивания в Telegram действует только для `/student/` и `/student/index.html`; служебные страницы сохраняют запрет встраивания.

## Постоянный HTTPS-домен

В **одинаковом окружении** веб-процесса и воркера задайте:

```dotenv
QALDYQ_PUBLIC_URL=https://qaldyq.example.kz
QALDYQ_DB=/srv/qaldyq/data/qaldyq-v5.4.sqlite3
TELEGRAM_BOT_USERNAME=Qalqyq_NOVA_bot
TELEGRAM_BOT_TOKEN=<локально из BotFather>
TELEGRAM_WEBHOOK_URL=https://qaldyq.example.kz/api/telegram/webhook
TELEGRAM_WEBHOOK_SECRET=<случайный секрет>
```

`QALDYQ_PUBLIC_URL` — origin без пути. Прежнее имя `QALDYQ_APP_URL` поддерживается для совместимости, но `QALDYQ_PUBLIC_URL` имеет приоритет. Ни адрес туннеля, ни localhost не зашиты в кнопки Mini App и уведомлений: адрес берётся из окружения отправляющего воркера. Если `TELEGRAM_WEBHOOK_URL` пуст, используется `<QALDYQ_PUBLIC_URL>/api/telegram/webhook`.

Направьте DNS домена на свой сервер и включите HTTPS reverse proxy к `127.0.0.1:8765`. Пример Caddy:

```caddyfile
qaldyq.example.kz {
    reverse_proxy 127.0.0.1:8765
}
```

В продакшене запускайте **два отдельных сервиса** с автоматическим рестартом, одинаковым WorkingDirectory и EnvironmentFile. Один веб-процесс нужен также потому, что текущие веб-сессии хранятся в памяти.

```bash
.venv/bin/python server.py
.venv/bin/python telegram_bot.py --mode webhook
```

Можно сохранить polling и на сервере, если так удобнее: наличие домена само по себе polling не запрещает. Но polling и webhook одновременно для одного токена не запускайте. При polling воркер снимает webhook, не удаляя ожидающие обновления. При webhook регистрирует HTTPS URL и секрет. Windows с постоянным доменом: `./start-telegram.ps1 -Mode webhook`; Cloudflare Tunnel при этом не нужен.

Webhook проверяет `X-Telegram-Bot-Api-Secret-Token` до чтения тела. Прокси должен сохранять заголовок. Без корректного секрета — 403; без настройки — 503. HTTP 200 отдаётся только после фиксации входящего обновления в SQLite. Секрет состоит из 32–256 символов `A-Z a-z 0-9 _ -`; создайте его локально: `python -c "import secrets; print(secrets.token_urlsafe(32))"`. Не включайте токен/секрет в URL или журналы. Проверьте `getWebhookInfo`: корректный URL, отсутствие `last_error_message`, уменьшение ожидающих обновлений.

Ноутбук после выключения не обслуживает бота. Для работы 24/7 процессы должны оставаться запущенными на сервере. Менеджер процессов, HTTPS и DNS настраиваются на вашем хостинге; этот коммит сам по себе сайт не разворачивает. Перед публичным использованием создайте реальные аккаунты и замените демо-пароли.

## Надёжность и общие данные

`external_links` и `subscriptions` — существующие единственные источники привязок и подписок. `telegram_links` — только SQL VIEW для транспорта, не копия данных. События заказов, выдачи и напоминания о получении уже ставятся `mod_student` в общий `outbox`. Возвраты измерений и периодов добавляют комментарий в ту же очередь в транзакции изменения статуса; сроки берутся из существующего `generate_reminders`.

Воркер арендует запись общего `outbox` на 120 секунд, проверяет подписку и активность аккаунта перед отправкой, а для служебных сообщений — ещё текущую роль и организацию. Повторы ограничены (по умолчанию 5), есть экспоненциальная задержка и учёт `retry_after`; постоянные ошибки остаются `failed`. Блокировка выключает подписки и очередь адресату. `/start` не включает подписки обратно.

Отдельная `telegram_outbox` содержит только ответы на команды и callback-ack для непривязанных/привязанных чатов; заказы и бизнес-уведомления в неё не копируются. `telegram_inbox.update_id` уникален. Изменение диалога, запись измерения, результат обработки update и постановка ответа фиксируются атомарно. Повтор update/нажатия и перезапуск не добавляют второе измерение. Создание заказа использует существующий уникальный `request_id`, проверку отпечатка, остатков, слота, срока и однократной выдачи с регистрацией продажи.

Отправка сообщений — **at least once**: авария между принятием сообщения Telegram и фиксацией `sent` может повторить сообщение, поскольку Bot API не поддерживает ключ идемпотентности отправки. Само измерение или заказ не повторяется. Следите за `failed`, возрастом очереди и диском; резервная копия включает общую SQLite с очередями.

## Проверки

```powershell
python tests/run_offline.py
python -m unittest discover -s tests -p test_telegram.py -v
node --test tests/telegram.test.cjs tests/app.test.cjs tests/offline.test.cjs tests/i18n.test.cjs
```

Первый запуск заменяет только сетевой транспорт существующих HTTP-тестов запросами в памяти: настоящий HTTP parser, Handler, реальные временные SQLite и общая доменная логика остаются. Telegram API подменён; не нужен токен и не создаются реальные заказы в рабочей базе. Для двух существующих тестов ML по-прежнему требуется scikit-learn из `requirements.txt`; код прогноза этим изменением не меняется. Если пакет недоступен, можно явно запустить `python tests/run_offline.py --skip-optional-ml`: только эти две проверки пометятся skipped с указанием причины. Проверка Windows launcher: `tests/test_telegram_launcher.ps1`.

Без токена воркер явно сообщает, что реальная отправка не проверена. Автоматические тесты не доказывают регистрацию webhook и работу клиента Telegram на вашем домене. После развёртывания проверьте: `/link`, измерение с фото, возврат с комментарием, Mini App, заказ, выдачу, `/stop`, блокировку и повтор webhook. Реальный токен не хранится в этом репозитории.

Официальные протоколы: [Mini App initData](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app), [aiogram](https://docs.aiogram.dev/en/latest/dispatcher/webhook.html).
